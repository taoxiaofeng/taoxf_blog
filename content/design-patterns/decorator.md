# 装饰器模式（Decorator）

**别名：** 装饰者、包装器（Wrapper）

## 意图

**装饰器模式**是一种结构型设计模式，允许你通过将对象放入包含行为的特殊封装对象中来为原对象绑定新的行为。

## 问题

假设你正在开发一个通知库，其他程序可以使用它向用户发送关于重要事件的通知。

通知库的最初版本基于 `通知器` Notifier 类，该类只有几个成员变量、一个构造函数和一个 `send` 发送方法。该方法可以从客户端接收消息参数，并将该消息发送给通过构造函数传入通知器的一组邮箱列表中的所有人。作为客户端的第三方程序仅会创建和配置通知器对象一次，然后在有重要事件发生时对其进行调用。

在某个时刻，你发现库的用户期望使用除邮件以外的方式接收通知。许多人希望收到关于紧急事件的手机短信，还有人希望在微信上收到通知，而公司用户则希望在 Slack 上获取通知。

这有什么难的呢？你扩展了 `通知器` 类，然后在新的子类中添加了额外的通知方法。现在客户端需要实例化所需的通知类并在后续的通知中使用它。

但是如果有人需要同时使用多种通知方式呢？例如，房子着火了你大概希望同时通过所有渠道获知。

你可以尝试创建一个特殊的子类来将多种通知方式组合在一起以解决该问题。但这样很快会导致代码量急剧膨胀，不仅仅是库代码，客户端代码也会如此。

你必须找到其他方式来组织通知类的结构，否则它们的数量会让 Guinness 纪录望尘莫及。

## 解决方案

当你需要更改一个对象的行为时，首先想到的方法就是扩展它所属的类。然而继承有几个严重的问题需要注意：

- 继承是静态的。你无法在运行时更改已有对象的行为，只能使用由不同子类创建的对象来替换它。
- 子类只能有一个父类。大部分编程语言不允许一个类同时继承多个类的行为。

其中一种解决方案是使用**组合**而非继承。两者的工作方式几乎相同：一个对象*引用*另一个对象并将部分工作委派给它；而继承中的对象*本身*就能完成这些工作，因为它继承了父类的行为。

使用这个新方法，你可以轻松地用另一个对象来替换各种连接的"助手"对象从而在运行时改变容器的行为。一个对象可以使用多个类的行为，包含多个指向其他对象的引用并将各种工作委派给它们。组合是许多设计模式背后的关键原则（包括装饰器在内）。

**封装器**是装饰模式的别名，这个名称清晰地表达了该模式的核心思想。"封装器"是一个能与目标对象连接的对象。封装器包含与目标对象相同的一组方法，它会将所有接收到的请求委派给目标对象。但封装器可以在将请求委派给目标前后对其进行处理，所以可能改变最终结果。

那么什么时候一个简单的封装器变成了真正的装饰器呢？正如刚才提到的，封装器实现了与其封装对象相同的接口。因此从客户端的角度来看这些对象是完全一样的。让封装器的引用成员变量可以是遵循该接口的任何对象。这使得你可以将一个对象放入多个封装器中，并在对象中添加所有这些封装器的组合行为。

在通知的例子中，我们可以将简单的邮件通知行为放在基础 `通知器` 类中，但将所有其他通知方法转化为装饰器。

## 结构

1. **部件（Component）** 声明封装器和被封装对象的公用接口。
2. **具体部件（Concrete Component）** 类是被封装对象所属的类。它定义了基础行为，但装饰类可以改变这些行为。
3. **基础装饰（Base Decorator）** 类拥有一个指向被封装对象的引用成员变量。该变量的类型应当被声明为通用部件接口，这样它就可以引用具体的部件和装饰。基础装饰器会将所有操作委派给被封装的对象。
4. **具体装饰类（Concrete Decorators）** 定义了可以动态添加到部件的额外行为。具体装饰类会重写装饰基类的方法，并在调用父类方法之前或之后进行额外的行为。
5. **客户端（Client）** 可以使用多层装饰来封装部件，只要它能使用通用接口与所有对象互动即可。

## 伪代码

```
// 装饰器可以改变组件接口所定义的操作。
interface DataSource is
    method writeData(data)
    method readData():data

// 具体组件提供了操作的默认实现。这些类在程序中可能
// 有多个变体。
class FileDataSource implements DataSource is
    constructor FileDataSource(filename) { ... }

    method writeData(data) is
        // 将数据写入文件。

    method readData():data is
        // 从文件读取数据。

// 装饰基类和其他组件遵循相同的接口。该类的主要任务是
// 定义所有具体装饰的封装接口。封装的默认实现代码中可能
// 会包含一个保存被封装组件的成员变量，并且负责对其进行
// 初始化。
class DataSourceDecorator implements DataSource is
    protected field wrappee: DataSource

    constructor DataSourceDecorator(source: DataSource) is
        wrappee = source

    method writeData(data) is
        wrappee.writeData(data)

    method readData():data is
        return wrappee.readData()

// 具体装饰器必须在被封装对象上调用方法，不过也可以自行
// 在结果中添加一些内容。装饰器可以在将请求传递给被封装
// 对象之前或之后执行附加行为。
class EncryptionDecorator extends DataSourceDecorator is
    method writeData(data) is
        // 1. 加密传入的数据。
        // 2. 将加密后的数据传递给被封装对象的 writeData
        //    方法。

    method readData():data is
        // 1. 从被封装对象的 readData 方法中获取数据。
        // 2. 如果数据被加密，则尝试解密。
        // 3. 返回结果。

class CompressionDecorator extends DataSourceDecorator is
    method writeData(data) is
        // 1. 压缩传入的数据。
        // 2. 将压缩后的数据传递给被封装对象的 writeData 方法。

    method readData():data is
        // 1. 从被封装对象的 readData 方法中获取数据。
        // 2. 如果数据被压缩，则进行解压缩。
        // 3. 返回结果。

// 客户端代码使用示例。
class Application is
    method dumbUsageExample() is
        source = new FileDataSource("somefile.dat")
        source.writeData(salaryRecords)

        source = new CompressionDecorator(source)
        source.writeData(salaryRecords)

        source = new EncryptionDecorator(source)
        // 写入目标文件的是压缩和加密后的数据。
        source.writeData(salaryRecords)
```

## 适用场景

- 如果你希望在无需修改代码的情况下即可使用对象，且希望在运行时为对象新增额外的行为，可以使用装饰模式。装饰能将业务逻辑组织为层次结构，你可以为各层创建一个装饰，在运行时将各种不同逻辑组合成对象。由于这些对象都遵循通用接口，客户端代码能以相同的方式使用这些对象。
- 如果用继承来扩展对象行为的方案难以实现或者根本不可行，你可以使用该模式。许多编程语言使用 `final` 关键字来限制对某个类的进一步扩展。对于用 `final` 修饰的类，复用已有行为的唯一方式就是使用装饰模式：用封装器对其进行封装。

## 实现步骤

1. 确保业务逻辑可用一个基本组件及多个额外可选层次表示。
2. 找出基本组件和可选层次中的通用方法。创建一个组件接口并在其中声明这些方法。
3. 创建一个具体组件类，并定义其基础行为。
4. 创建装饰基类，使用一个成员变量存储指向被封装对象的引用。该成员变量必须被声明为组件接口类型，从而能在运行时连接具体组件和装饰。装饰基类必须将所有工作委派给被封装的对象。
5. 确保所有类都实现组件接口。
6. 将装饰基类扩展为具体装饰。具体装饰必须在调用父类方法（总是委派给被封装对象）之前或之后执行自身的行为。
7. 客户端代码负责创建装饰并将其组合成客户端所需的形式。

## 优缺点

### 优点

- 无需创建新子类即可扩展对象的行为。
- 你可以在运行时添加或删除对象的功能。
- 你可以用多个装饰封装对象来组合几种行为。
- **单一职责原则。** 你可以将实现了许多不同行为的大类拆分为多个较小的类。

### 缺点

- 在封装器栈中删除特定封装器比较困难。
- 实现行为不受装饰栈顺序影响的装饰比较困难。
- 各层的初始化配置代码看上去可能会很糟糕。

## 与其他模式的关系

- **适配器模式**可以对已有对象的接口进行修改，**装饰器模式**则能在不改变对象接口的前提下强化对象功能。此外装饰器还支持递归组合，适配器则无法实现。
- **适配器**能为被封装对象提供不同的接口，**代理模式**能为对象提供相同的接口，**装饰器**则能为对象提供加强的接口。
- **责任链模式**和**装饰器模式**的类结构非常相似。两者都依赖递归组合将需要执行的操作传递给一系列对象。但两者有几个重要不同：责任链的管理者可以相互独立地执行一切操作，还可以随时停止传递请求。而各种装饰器可以在遵循基本接口的情况下扩展对象的行为，并且装饰器无法中断请求的传递。
- **组合模式**和**装饰器**的结构图很相似，因为两者都依赖递归组合来组织无限数量的对象。装饰器类似于组合，但其只有一个子组件。
- 大量使用**组合**和**装饰器**的设计通常可以从使用**原型模式**中获益。你可以通过该模式来复制复杂结构，而非从零开始重新构造。
- **装饰器**可让你更改对象的外表，**策略模式**则让你能够改变其本质。
