# 单例模式（Singleton）

## 意图

**单例**是一种创建型设计模式，让你能够保证一个类只有一个实例，并提供一个访问该实例的全局节点。

## 问题

单例模式同时解决了两个问题，但违反了**单一职责原则**：

1. **保证一个类只有一个实例。** 为什么有人要控制一个类的实例数量？最常见的原因是控制对某些共享资源的访问——例如数据库或文件。其工作方式是：假设你创建了一个对象，过了一段时间后决定创建一个新对象。此时你不会得到一个全新的对象，而是会得到之前已经创建的那个对象。注意，这种行为无法通过普通构造函数实现，因为从设计上说，构造函数调用**必须**返回一个新对象。

2. **为该实例提供一个全局访问节点。** 还记得那些用来存储重要对象的全局变量吗？虽然它们非常方便，但也很不安全，因为任何代码都有可能覆盖变量的内容从而导致程序崩溃。和全局变量一样，单例模式允许你在程序的任何地方访问某个对象。但它同时也保护该实例不被其他代码覆盖。

如今，单例模式已经变得非常流行，甚至即使只解决了上述问题之一，人们也可能将其称为单例。

## 解决方案

所有单例的实现都有以下两个共同步骤：

- 将默认构造函数设为私有，以防止其他对象使用 `new` 运算符创建该类的实例。
- 创建一个充当构造函数的静态创建方法。该方法内部会调用私有构造函数来创建对象，并将其保存在一个静态字段中。之后所有对该方法的调用都会返回这个缓存的对象。

如果你的代码能够访问单例类，那它就能调用该单例的静态方法。每次调用该方法时，总会返回相同的对象。

## 现实世界类比

政府是单例模式的一个很好的例子。一个国家只能有一个官方政府。无论组成政府的个人的身份如何，"X 国政府"这个称谓就是一个标识当权者群体的全局访问节点。

## 结构

1. **单例（Singleton）** 类声明了一个名为 `getInstance`（获取实例）的静态方法来返回其所属类的同一实例。单例的构造函数必须对客户端代码隐藏。调用 `getInstance` 方法应该是获取单例对象的唯一方式。

## 伪代码

在本示例中，数据库连接类作为一个**单例**。该类没有公有构造函数，因此获取其对象的唯一方式是调用 `getInstance` 方法。该方法缓存首次创建的对象，并在所有后续调用中返回它。

```
// 数据库类定义了 `getInstance` 方法，
// 让客户端在整个程序中访问同一数据库连接实例。
class Database is
    // 用于存储单例实例的字段应声明为静态。
    private static field instance: Database

    // 单例的构造函数应始终为私有，
    // 以防止通过 `new` 运算符直接构造调用。
    private constructor Database() is
        // 一些初始化代码，如连接数据库服务器。
        // ...

    // 控制对单例实例访问的静态方法。
    public static method getInstance() is
        if (Database.instance == null) then
            acquireThreadLock() and then
                // 确保在当前线程等待锁释放期间，
                // 实例未被另一个线程初始化。
                if (Database.instance == null) then
                    Database.instance = new Database()
        return Database.instance

    // 最后，任何单例都应定义一些可在其实例上
    // 执行的业务逻辑。
    public method query(sql) is
        // 例如，应用的所有数据库查询都通过此方法执行。
        // 因此你可以在此放置节流或缓存逻辑。
        // ...

class Application is
    method main() is
        Database foo = Database.getInstance()
        foo.query("SELECT ...")
        // ...
        Database bar = Database.getInstance()
        bar.query("SELECT ...")
        // 变量 `bar` 将包含与变量 `foo` 相同的对象。
```

## 适用场景

- 当程序中的某个类只应有一个可供所有客户端使用的实例时（例如，程序各部分共享的一个数据库对象），可使用单例模式。
- 当你需要更严格地控制全局变量时，可使用单例模式。

## 实现步骤

1. 在类中添加一个用于存储单例实例的私有静态字段。
2. 声明一个用于获取单例实例的公有静态创建方法。
3. 在静态方法中实现"延迟初始化"。它应在首次调用时创建新对象并将其放入静态字段中。此后该方法的每次调用都应返回该实例。
4. 将类的构造函数设为私有。该类的静态方法仍可调用构造函数，但其他对象不行。
5. 检查客户端代码，将对单例构造函数的所有直接调用替换为对其静态创建方法的调用。

## 优缺点

### 优点

- 你可以确保一个类只有一个实例。
- 你获得了该实例的一个全局访问节点。
- 单例对象仅在首次被请求时才会初始化。

### 缺点

- 违反了**单一职责原则**。该模式同时解决了两个问题。
- 单例模式可能掩盖不良设计，例如程序组件之间过于了解彼此。
- 该模式在多线程环境中需要特殊处理，以防止多个线程多次创建单例对象。
- 单例的客户端代码可能难以进行单元测试，因为许多测试框架依赖继承来创建模拟对象。由于单例类的构造函数是私有的，且大多数语言无法重写静态方法，你需要想出创造性的方式来模拟单例。

## 与其他模式的关系

- **外观**类通常可以转化为**单例**，因为大多数情况下只需要一个外观对象。
- 如果能将对象的所有共享状态简化为一个享元对象，那么**享元**与**单例**类似。但两者有本质区别：单例实例只有一个，而享元类可以有多个具有不同内在状态的实例；单例对象可以是可变的，享元对象是不可变的。
- **抽象工厂**、**建造者**和**原型**都可以用**单例**模式实现。
