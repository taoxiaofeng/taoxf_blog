# 工厂方法模式（Factory Method）

**别名：** 虚拟构造函数（Virtual Constructor）

## 意图

**工厂方法**是一种创建型设计模式，其在父类中提供一个创建对象的方法，允许子类决定实例化对象的类型。

## 问题

假设你正在开发一款物流管理应用程序。最初版本只能处理卡车运输，因此大部分代码都在 `卡车` 类中。

一段时间后，应用变得非常流行。每天你都会收到来自海运公司的大量请求，希望能将海上物流功能整合到应用中。

如果代码的其余部分已经与现有类耦合，那么向程序中添加新类并非易事。

好消息，对吧？但是代码怎么办？目前大部分代码都与 `卡车` 类相耦合。向应用中添加 `轮船` 类需要修改整个代码库。而且如果后续你需要增加另一种运输方式，可能又得重复所有修改。

结果就是，你会写出一堆充满条件分支的臃肿代码，这些代码根据运输对象的类型来切换应用的行为。

## 解决方案

工厂方法模式建议使用特殊的**工厂方法**来代替直接的对象构造调用（使用 `new` 运算符）。别担心：对象仍然是通过 `new` 运算符创建的，只是改为在工厂方法中调用。工厂方法返回的对象通常被称为**产品**。

子类可以修改工厂方法返回的对象类型。

乍一看，这种改变似乎毫无意义：我们只是将构造函数调用从程序的一个位置移动到了另一个位置。但请考虑：现在你可以在子类中重写工厂方法，从而改变该方法所创建的产品类型。

但有一个小限制：仅当这些产品具有共同的基类或接口时，子类才能返回不同类型的产品。同时，基类中的工厂方法的返回类型应声明为该接口。

例如，`卡车` 和 `轮船` 类都应实现 `运输` 接口，该接口声明了一个名为 `deliver`（交付）的方法。每个类以不同的方式实现该方法：卡车通过陆路运送货物，轮船通过海路运送货物。`陆路物流` 类中的工厂方法返回卡车对象，而 `海路物流` 类中的工厂方法返回轮船对象。

只要所有产品类都实现了同一接口，你就可以将其对象传递给客户端代码而不会破坏它。

使用工厂方法的代码（通常称为**客户端**代码）不会感知到不同子类返回的实际产品之间的差异。客户端将所有产品视为抽象的 `运输` 对象。客户端知道所有运输对象都应有 `deliver` 方法，但该方法具体如何工作并不重要。

## 结构

1. **产品（Product）** 将会对接口进行声明。对于所有由创建者及其子类构建的对象，这些接口都是通用的。
2. **具体产品（Concrete Products）** 是产品接口的不同实现。
3. **创建者（Creator）** 类声明返回产品对象的工厂方法。该方法的返回类型必须与产品接口相匹配。你可以将工厂方法声明为抽象方法，强制所有子类各自实现该方法。作为替代方案，基础工厂方法可以返回某个默认产品类型。注意，尽管名称如此，产品创建并**不是**创建者的主要职责。通常创建者类已经拥有与产品相关的核心业务逻辑。工厂方法将这些逻辑与具体产品类解耦。
4. **具体创建者（Concrete Creators）** 重写基础工厂方法，使其返回不同类型的产品。注意，工厂方法不一定每次都创建新的实例，它也可以返回缓存、对象池或其他来源中的已有对象。

## 伪代码

本示例演示了如何使用工厂方法创建跨平台的 UI 元素，同时不会将客户端代码与具体 UI 类相耦合。

基类 `Dialog` 使用不同的 UI 元素来渲染其窗口。在不同的操作系统下，这些元素的外观可能略有不同，但其行为应保持一致。Windows 中的按钮在 Linux 中仍然是按钮。

当工厂方法发挥作用时，你无需为每个操作系统重写 `Dialog` 类的逻辑。如果我们在基类 `Dialog` 中声明了一个生产按钮的工厂方法，随后可以创建一个子类，从该工厂方法中返回 Windows 风格的按钮。该子类继承了基类中的大部分代码，但借助工厂方法，它能够在屏幕上渲染 Windows 风格的按钮。

要使该模式生效，基类 `Dialog` 必须使用抽象按钮（即所有具体按钮遵循的基类或接口）。这样，`Dialog` 中的代码无论使用哪种类型的按钮都能正常工作。

```
// 创建者类声明的工厂方法必须返回一个产品类的对象。
// 创建者的子类通常会提供该方法的实现。
class Dialog is
    // 创建者也可以提供工厂方法的默认实现。
    abstract method createButton():Button

    // 请注意，创建者的主要职责并非创建产品。
    // 其中通常会包含一些核心业务逻辑，这些逻辑
    // 依赖于由工厂方法返回的产品对象。子类可以
    // 通过重写工厂方法并返回不同类型的产品来间接
    // 修改业务逻辑。
    method render() is
        // 调用工厂方法创建一个产品对象。
        Button okButton = createButton()
        // 现在使用产品。
        okButton.onClick(closeDialog)
        okButton.render()

// 具体创建者重写工厂方法以改变其所返回的产品类型。
class WindowsDialog extends Dialog is
    method createButton():Button is
        return new WindowsButton()

class WebDialog extends Dialog is
    method createButton():Button is
        return new HTMLButton()

// 产品接口声明了所有具体产品都必须实现的操作。
interface Button is
    method render()
    method onClick(f)

// 具体产品提供了产品接口的各种实现。
class WindowsButton implements Button is
    method render(a, b) is
        // 以 Windows 风格渲染按钮。
    method onClick(f) is
        // 绑定本地操作系统的点击事件。

class HTMLButton implements Button is
    method render(a, b) is
        // 返回按钮的 HTML 表现形式。
    method onClick(f) is
        // 绑定网页浏览器的点击事件。

class Application is
    field dialog: Dialog

    // 应用程序根据当前配置或环境设置选择创建者的类型。
    method initialize() is
        config = readApplicationConfigFile()
        if (config.OS == "Windows") then
            dialog = new WindowsDialog()
        else if (config.OS == "Web") then
            dialog = new WebDialog()
        else
            throw new Exception("错误！未知的操作系统。")

    // 客户端代码通过基础接口与具体创建者的实例进行交互。
    // 只要客户端通过基础接口与创建者进行交互，
    // 你就可以将任何创建者的子类传递给客户端。
    method main() is
        this.initialize()
        dialog.render()
```

## 适用场景

- 当你在编写代码时无法预知对象的确切类型及其依赖关系时，可使用工厂方法。工厂方法将产品构造代码与实际使用产品的代码分离，从而能够在不影响其他代码的情况下扩展产品构造逻辑。
- 当你希望为库或框架的用户提供扩展其内部组件的方式时，可使用工厂方法。
- 当你希望通过复用现有对象来节省系统资源，而非每次都重新创建对象时，可使用工厂方法。

## 实现步骤

1. 让所有产品遵循同一接口。该接口应声明对每种产品都有意义的方法。
2. 在创建者类中添加一个空的工厂方法。该方法的返回类型应与通用产品接口一致。
3. 在创建者代码中找到对产品构造函数的所有引用。逐一将其替换为对工厂方法的调用，同时将产品创建代码提取到工厂方法中。
4. 现在，为工厂方法中列出的每种产品类型创建一组创建者子类，并在子类中重写工厂方法，将基础方法中对应的构造代码提取出来。
5. 如果产品类型过多，且为所有产品创建子类没有意义，你可以在子类中复用基类中的控制参数。
6. 如果提取所有代码后，基础工厂方法变为空方法，你可以将其设为抽象方法。如果还有剩余代码，可以将其设为该方法的默认行为。

## 优缺点

### 优点

- 你可以避免创建者和具体产品之间的紧密耦合。
- **单一职责原则。** 你可以将产品创建代码集中到程序中的一个位置，从而使代码更易于维护。
- **开闭原则。** 你无需更改现有客户端代码，就能在程序中引入新的产品类型。

### 缺点

- 应用工厂方法模式需要引入许多新的子类，可能会导致代码变得更加复杂。最好的情况是将该模式引入创建者类的现有层次结构中。

## 与其他模式的关系

- 许多设计在初期使用**工厂方法**（较为简单，可通过子类进行定制），随后逐渐演变为**抽象工厂**、**原型**或**建造者**（更灵活但更复杂）。
- **抽象工厂**类通常基于一组**工厂方法**，但你也可以使用**原型**来组合这些类上的方法。
- 你可以将**工厂方法**与**迭代器**一起使用，让集合子类返回与集合兼容的不同类型的迭代器。
- **原型**不基于继承，因此没有继承的缺点。另一方面，原型需要对克隆对象进行复杂的初始化。**工厂方法**基于继承，但不需要初始化步骤。
- **工厂方法**是**模板方法**的一种特殊形式。同时，工厂方法可以作为大型模板方法中的一个步骤。
