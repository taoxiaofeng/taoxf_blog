# 适配器模式（Adapter）

**别名：** 封装器（Wrapper）

## 意图

**适配器模式**是一种结构型设计模式，它能使接口不兼容的对象能够相互合作。适配器让原本由于接口不兼容而不能一起工作的类可以协同工作。

## 问题

假设你正在开发一款股票市场监控程序。它从不同来源下载 XML 格式的股票数据，然后向用户呈现出美观的图表和信息图。

在某个阶段，你决定集成一个智能分析第三方库来改善应用。但问题是，该分析库只能处理 JSON 格式的数据。

你可以修改该库使其支持 XML。但这可能会破坏依赖该库的现有代码。更糟糕的是，你可能根本无法访问该库的源代码，这使得上述方案完全不可行。

## 解决方案

你可以创建一个**适配器**。这是一个特殊的对象，能够转换对象的接口，使其能与其他对象进行交互。

适配器包装一个对象，从而隐藏了转换的复杂性。被包装的对象甚至不知道适配器的存在。例如，你可以使用一个将所有数据转换为 JSON 格式的适配器来包装以 XML 格式操作的对象。

适配器不仅可以转换不同格式的数据，还有助于采用不同接口的对象之间的合作。它的运作方式如下：

1. 适配器实现与其中一个现有对象兼容的接口。
2. 现有对象可以使用该接口安全地调用适配器方法。
3. 适配器方法被调用后将以另一个对象兼容的格式和顺序将请求传递给该对象。

有时你甚至可以创建一个双向适配器来实现双向转换调用。

## 结构

### 对象适配器

该实现使用了组合原则：适配器实现了其中一个对象的接口，并对另一个对象进行封装。所有流行的编程语言都可以实现。

1. **客户端（Client）** 是包含当前程序业务逻辑的类。
2. **客户端接口（Client Interface）** 描述了其他类与客户端代码合作时必须遵循的协议。
3. **服务（Service）** 中有一些有用的类（通常来自第三方或遗留系统）。客户端与其接口不兼容，因此无法直接调用其功能。
4. **适配器（Adapter）** 是一个可以同时与客户端和服务交互的类：它在实现客户端接口的同时封装了服务对象。适配器接收客户端通过适配器接口发起的调用，并将其转换为适用于被封装服务对象的调用。
5. 客户端代码只需通过客户端接口与适配器交互，无需与具体的适配器类耦合。因此你可以向程序中添加新类型的适配器而无需修改现有代码。当服务类的接口被更改或替换时这很有用：你无需修改客户端代码就能创建新的适配器类。

### 类适配器

该实现使用了继承机制：适配器同时继承两个对象的接口。请注意，这种方式仅能在支持多重继承的编程语言（如 C++）中实现。

1. **类适配器**不需要封装任何对象，因为它同时继承了客户端和服务的行为。适配在重写的方法中完成。最终生成的适配器可以替代已有的客户端类使用。

## 伪代码

```
// 假设你有两个接口兼容的类：圆孔和圆钉。
class RoundHole is
    constructor RoundHole(radius) { ... }

    method getRadius() is
        // 返回孔的半径。

    method fits(peg: RoundPeg) is
        return this.getRadius() >= peg.getRadius()

class RoundPeg is
    constructor RoundPeg(radius) { ... }

    method getRadius() is
        // 返回钉的半径。

// 但还有一个不兼容的类：方钉。
class SquarePeg is
    constructor SquarePeg(width) { ... }

    method getWidth() is
        // 返回方钉的宽度。

// 适配器类让你能将方钉放入圆孔中。
// 它扩展了 RoundPeg 类以使适配器对象可以充当圆钉。
class SquarePegAdapter extends RoundPeg is
    // 实际上，适配器中包含一个方钉类的实例。
    private field peg: SquarePeg

    constructor SquarePegAdapter(peg: SquarePeg) is
        this.peg = peg

    method getRadius() is
        // 适配器假装自己是一个圆钉，
        // 半径刚好能容下适配器实际封装的方钉。
        return peg.getWidth() * Math.sqrt(2) / 2

// 客户端代码中的某处。
hole = new RoundHole(5)
rpeg = new RoundPeg(5)
hole.fits(rpeg) // true

small_sqpeg = new SquarePeg(5)
large_sqpeg = new SquarePeg(10)
// hole.fits(small_sqpeg) // 无法编译（不兼容的类型）

small_sqpeg_adapter = new SquarePegAdapter(small_sqpeg)
large_sqpeg_adapter = new SquarePegAdapter(large_sqpeg)
hole.fits(small_sqpeg_adapter) // true
hole.fits(large_sqpeg_adapter) // false
```

## 适用场景

- 当你希望使用某个现有类，但其接口与你的代码不兼容时，可以使用适配器类。适配器模式允许你创建一个中间层类，其可作为代码与遗留类、第三方库或任何其他接口奇异类之间的转换器。
- 当你希望复用这样一些类，他们处于同一层次结构，并且他们又有额外的一些共同行为，但该行为无法被加入到超类中时，你可以使用该模式。你可以扩展每个子类，将缺失的行为添加到新的子类中。但你需要在所有新类中复制代码，这样会有很多坏味道。将缺失的行为放入适配器类中是更优雅的解决方案。

## 实现步骤

1. 确保至少有两个类存在不兼容的接口：一个有用的**服务**类和一个或多个将受益于使用该服务类的**客户端**类。
2. 声明客户端接口，描述客户端如何与服务交互。
3. 创建适配器类并让其遵循客户端接口。先将所有方法留空。
4. 在适配器类中添加一个成员变量用于存储对服务对象的引用。通常在构造函数中初始化该成员变量，但有时在调用其方法时将它传递给适配器更为方便。
5. 逐一实现适配器类中客户端接口的所有方法。适配器应当委派实际工作给服务对象，自身仅处理接口或数据格式的转换。
6. 客户端应通过客户端接口使用适配器。这样你就能在不影响客户端代码的情况下修改或扩展适配器。

## 优缺点

### 优点

- **单一职责原则。** 你可以将接口或数据转换代码从程序主要业务逻辑中分离。
- **开闭原则。** 只要客户端代码通过客户端接口与适配器进行交互，你就能在不修改现有客户端代码的情况下在程序中添加新类型的适配器。

### 缺点

- 代码整体复杂度增加，因为你需要新增一系列接口和类。有时直接更改服务类使其与其他代码兼容会更简单。

## 与其他模式的关系

- **桥接模式**通常在设计初期使用，让你可以将程序的各个部分独立开来开发。另一方面，**适配器模式**通常在已有程序中使用，让一些不兼容的类能一起合作。
- **适配器**可以对已有对象的接口进行修改，**装饰器模式**则能在不改变对象接口的前提下强化对象功能。此外，装饰器还支持递归组合，适配器则无法实现。
- **适配器**能为被封装对象提供不同的接口，**代理模式**能为对象提供相同的接口，**装饰器**则能为对象提供增强的接口。
- **外观模式**为现有对象定义了一个新接口，**适配器**则会复用现有的接口。适配器通常只封装一个对象，外观通常会作用于整个对象子系统上。
- **桥接**、**状态**和**策略模式**（某种程度上包括**适配器**）的接口非常相似。实际上，它们都基于组合原则——即将工作委派给其他对象，不过它们各自解决的问题不同。
